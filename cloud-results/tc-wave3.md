## Deviations and decisions (read these)
1. **Tovu wiring differs from the sheet text.** The sheet asks for "one deps line in `delegatedToolRouteDeps`" and "the scope file grows by one line at most". The size ratchet counts `createSiteScope#1` at 828 and the file at 945 (both exactly at their baseline), so any added non-blank line in `agent-daemon-scope.ts` would print a new `Worsened violation`. I put the port on `siteTools` instead (`createDaemonSiteTools` returns `families: createContentReadFamilyPort({ registry })`, appended to the existing `return` line) and changed the one existing deps line to `toolRegistry: siteTools.registry, toolFamilies: siteTools.families,`. Net line counts of both functions and both files are unchanged; the import lands in `agent-daemon-site-tools.ts` (166 lines, no debt). The port is built over the same run-scoped registry the route decides with (a test shows it fails closed outside a live run).
2. `toolCandidates` gets the optional `target` the sheet names. The only caller that passes it is `resolveToolTarget` (the member a family selector points at, via new `selectedFamilyMember`); this keeps `ToolTarget.candidates` ranked as before. `ReadOnlyToolCheckRequired.input` (the old hint field) and `assertKnownTool`'s `input` are removed: nothing in either repo passed `input` to `checkReadOnlyTool`.
3. Public types: `ToolFamilyPort`, `ToolFamilyDescription`, `FamilySelector` are exported from `@jini-ai/daemon/http` (one `export type` line in the existing `http/index.ts`, because Tovu types its port against it). Not a forwarder shell: the types are defined in `core/tool-family.ts`.
4. Guard: new constant `HOST_TOOL_NAMES = ['content_read']` in `scripts/check-engine-boundaries.ts` (rule R5-neutrality, non-test files only, comments stripped as for the other R5 strings). `packages/db/src/tools/database-catalog.ts` mentions the id only in a comment, so it does not trip.
5. **A real bug the sheet's case 7 found:** for a published tool whose wire name differs from its id and whose id equals an MCP-local tool name (`search_tools`), the typed tool's gateway resolved the registry id to the local tool and ran it (`search_tools_1` ran `search_tools`). `createTypedDelegatedToolTool` now strips local resolution when `wireName !== descriptor.id`, so the call reaches the daemon with the registry id. When names agree the local entry is the tool itself, and stripping there would change clamp/normalization (a wave2a test caught this; not done).
6. `describe_tool` validates the daemon's answer for the described id when the host publishes (as before). A host without `publishTool` that gets an answer that is not this tool's descriptor still passes it through unchanged (kept: several credential-propagation tests rely on it); a valid descriptor there now also gets `callAs` / `call` (gateway form).
7. `run-tool-host.ts` startup collector now has to return a `ToolPublication`; it returns `{ skipped: 'not-found' }` (it only collects; the exposure built from its list decides, and its describe result is discarded). Commented there.
