## 1. Mechanism — the full path of a call

### 1.1 What is, and isn't, novamira

The Abilities API (`wp_register_ability`, `WP_Ability::execute()`) is **WordPress core**, not a
novamira invention — verified against a real core clone:
`/Users/la/Programming/OSS-Repos/wordpress/src/wp-includes/abilities-api.php:278` and
`abilities-api/class-wp-ability.php`. `WP_Ability::execute()` (class-wp-ability.php:734-830) runs a
fixed core-enforced pipeline for *every* ability on the system, novamira's included:

```
normalize_input() -> validate_input() -> check_permissions() -> do_execute() -> validate_output()
```

`check_permissions()` (class-wp-ability.php:588-621) calls the registered `permission_callback` and
requires it to return the literal boolean `true`; anything else (including a `WP_Error`) is coerced
to denial (class-wp-ability.php:788-804). This is real, load-bearing enforcement infrastructure that
sits underneath everything novamira does — the plugin did not have to build its own dispatch-time
authorization gate, it only had to write correct `permission_callback`s.

`wordpress/mcp-adapter` v0.5.0 (`composer.lock:919-924`, `github.com/WordPress/mcp-adapter`) is the
actual MCP transport/JSON-RPC layer, and it is a **separate, unvendored dependency** — I cannot read
its source. What I *can* confirm from usage sites in `novamira.php`:

### 1.2 Transport: three MCP servers, three tools each

`novamira.php:645-674` gates all of this on `novamira_is_enabled()`. Three MCP servers are registered:

| server | route | auth | novamira.php |
|---|---|---|---|
| canonical | `/mcp/novamira` | WP core Application Passwords | mcp-adapter default server config, `:650-658` |
| legacy alias | `/mcp/mcp-adapter-default-server` | same as canonical | `novamira_register_legacy_mcp_server`, `:683-700` |
| OAuth-only | `/mcp/novamira-oauth` | Bearer + league/oauth2-server | `novamira_register_oauth_mcp_server`, `:711-732` |

**The most important structural fact, and one that corrects a naive reading of "13 abilities = 13
MCP tools": the MCP tool surface is exactly three generic meta-tools**, not one tool per ability:

```php
// novamira.php:756-760
[
    'mcp-adapter/discover-abilities',
    'mcp-adapter/get-ability-info',
    'mcp-adapter/execute-ability',
]
```

These are provided by the (unread) vendor package and dispatch into the WP Abilities registry by
`ability_name`. This is confirmed for the two *mirror* servers (legacy alias, OAuth) — their tool list
is hardcoded to exactly these three (`novamira.php:756-760`), while their resources/prompts are
auto-discovered from every ability with `meta.mcp.public===true` of the matching type
(`novamira_discover_public_abilities`, `novamira.php:771-787`, explicitly said to
"Replicate `DefaultServerFactory::discover_abilities_by_type`," `novamira.php:766-767`).

**What I could not resolve, and am flagging as an open inference gap rather than asserting either
way:** whether the *canonical* default server (`/mcp/novamira`, built by the vendor's unread
`DefaultServerFactory`) also exposes only these 3 meta-tools, or additionally registers each public
ability as its own individually-named MCP tool. The comment at `novamira.php:734-738` claims the
mirrors have "same tools, resources, and prompts" as the canonical server, which — if taken literally
— implies the canonical server *also* only exposes the 3 meta-tools, meaning **the entire "13
abilities" surface is dispatched through `execute-ability` by name, never listed as 13 separate MCP
tool schemas.** I did not find a way to verify this without the vendor source. Either way, it settles
one open question from the survey cleanly: this is a **meta-tool/dispatch pattern**, structurally
close to what Jini's own `PROP-tool-catalog-discovery` proposes (`search_tools`/`describe_tool`/
`activate_tools`/`execute_tool`), not a flat 13-tool MCP surface.

### 1.3 Auth: two independent paths converge on the same WP capability check

**Application Password path** (`/mcp/novamira`): no novamira-specific auth code at all. WP core's
built-in Application Passwords REST authentication resolves a `WP_User` from the request; any user
who has (or was given) an application password authenticates as themselves.

**OAuth path** (`/mcp/novamira-oauth`), fully traced in `includes/oauth/middleware.php` and
`includes/oauth/bridge.php`:

1. `middleware.php:21-25` hooks `rest_authentication_errors` (prio 20) and `rest_pre_dispatch` (prio 10).
2. `authenticate()` (middleware.php:72-123) only engages for a Bearer header on a
   `/mcp/novamira-oauth*` route (`is_mcp_route`, middleware.php:132-135 — carefully distinguished from
   the canonical `/mcp/novamira` by requiring the `-oauth` suffix, not a loose prefix match).
3. Validates the token via league/oauth2-server's `ResourceServer::validateAuthenticatedRequest()`
   against a PSR-7 request built from PHP superglobals (`bridge.php:65-88`, since `WP_REST_Request`
   isn't available yet at this hook).
4. Checks the RFC 8707 audience: `oauth_client_id` must equal `resource_identifier()` =
   `rest_url('mcp/novamira-oauth')` (middleware.php:94-99, `oauth.php:20-23`) — a token minted for a
   different resource is rejected here.
5. Checks scope contains `mcp` (middleware.php:100-103, `has_mcp_scope`).
6. Extracts `oauth_user_id`, calls `wp_set_current_user($user_id)` (middleware.php:104-109) — **then
   re-checks `novamira_current_user_can_manage()` independently** (middleware.php:110,
   `helpers.php:637-640` = `is_super_admin()` on multisite else `current_user_can('manage_options')`).
   A valid, correctly-scoped, correct-audience token for a non-admin WP user is still rejected here.

Either path lands at the same final gate every individual ability enforces itself:
`novamira_permission_callback` (`helpers.php:953-960`) = `novamira_is_enabled() &&
novamira_current_user_can_manage()`. **OAuth adds transport-level cryptography (audience binding,
signed tokens, RFC 6750 challenge headers) but adds no fine-grained authorization**: the `mcp` scope
is boolean, and `supported_scopes()` (`oauth.php:46-49`) accepts `read`/`write` from some clients but
flattens every issued token to `mcp` regardless — "Access is all-or-nothing, so the extra scopes
grant nothing" (comment, verbatim). An OAuth token is exactly as powerful as an Application Password
for the same underlying admin — no capability it grants that the WP user didn't already have.

### 1.4 Dispatch and response

Once authenticated, the meta-tool (`execute-ability`, vendor-implemented, unread) presumably calls
`WP_Ability::execute($input)` for the named ability, which runs the core pipeline in §1.1, invoking
the ability's own `execute_callback` and returning its array/`WP_Error` result back through the
adapter to MCP JSON-RPC response framing (also vendor, unread).

## 3. `discover-abilities` — how discovery actually works

`includes/abilities/discover-abilities.php` (full file read). It is not an *addition* — it
unregisters the vendor's own `mcp-adapter/discover-abilities` ability and re-registers under the
identical name (lines 22-31), i.e. a hard override, not a second tool.

The mechanism (lines 73-102) is a **flat, unfiltered, unpaginated dump**: iterate `wp_get_abilities()`,
keep every ability where `meta.mcp.public === true` and `meta.mcp.type` is `tool` (default), return
`{name, label, description}` for each. No search query parameter, no ranking, no categories, no
pagination, no result cap. Alongside the list it attaches a large prose block
(`novamira_build_server_instructions()`, `helpers.php:1057-1119`) — but only if the caller has
`manage_options` (discover-abilities.php:91) — whose literal first line is:

> "Novamira gives you unrestricted control over this WordPress installation." (`helpers.php:1060`)

This is the primary mechanism for conveying "how to use this / safety rules" to the model — it is
100% prose, delivered once at first discovery, not re-enforced at call time.

**A genuine, if minor, asymmetry worth flagging**: `discover-abilities`'s own permission check is
weaker than the 12 abilities it lists. It only requires `is_user_logged_in()` plus
`current_user_can($cap)` where `$cap` defaults to `'read'` — a capability essentially every WP role
(down to Subscriber) has. So on the Application-Password transport, a low-privilege authenticated
user who was issued an application password can enumerate the names and descriptions of
`execute-php`, `run-wp-cli`, `delete-file`, etc. even though *invoking* any of them still requires
`manage_options` downstream. This is reconnaissance/information disclosure, not an execution bypass —
but it is a real, citable gap between "who can see the menu" and "who can order."

**Comparison to Jini's own design.** `ai-control-plane.md §10.1-10.2` and
`PROP-tool-catalog-discovery-2026-07-26.md §6.1` specify a **staged** discovery contract:
`search_tools(query, limit)` returns summaries only, filtered by principal/scope *before* ranking;
`describe_tool(id)` is paid for only on survivors; a fixed per-run tool budget (5-15) is the target.
Novamira's `discover-abilities` has no query, no limit, and no staging — it is a single call that
returns the entire visible catalog every time, unfiltered by task relevance (only by static
`mcp.public` metadata) and unranked. Structurally, though, the *3-meta-tool* shape it sits inside
(discover/get-info/execute) is close in spirit to Jini's proposed permanent verb set — novamira
independently arrived at "a small number of dispatch tools over a larger registry," it just didn't
carry that discipline into the discovery tool's own behavior.

## 4. The Gutenberg pending-change / finalization flow

**This corrects the dispatch prompt's stated hypothesis.** It is not a human-in-the-loop
*review/approval* pattern. It is a browser-hosted **JavaScript execution runtime requirement**,
dressed in queue/dashboard language. The human's role is infrastructural (keep a tab open), not
evaluative (there is no approve/reject/diff/preview anywhere in the flow).

**Why a browser is needed at all**: Gutenberg block serialization to the `post_content` HTML-comment
format depends on each registered block's own client-side JS `save()` function. There is no
general server-side PHP equivalent for arbitrary third-party blocks (WooCommerce, ACF, Kadence,
etc.), so novamira cannot serialize them itself in PHP — it has to borrow a real block editor running
in a real browser.

**Flow, traced through the actual files**:

1. `novamira/gutenberg-add-pending-change` (auto-creates a batch if `batch_id` omitted) accepts
   structured block specs (`{name, attributes, innerBlocks}`), stores them on a batch `WP_Post`
   (status `draft`). Raw-HTML-only content is **refused** unless `allow_raw_html=true`
   (add-pending-change.php:123-133) — real code, not a prose ask.
2. `novamira/gutenberg-enable-batch-finalization` flips the batch (and its items) to `ready`
   (enable-batch-finalization.php:92-96).
3. The **Block Editor Queue** admin page (`includes/gutenberg-finalizer-admin.php`) polls
   `/gutenberg/batches/claim-next` **automatically every 5 seconds**
   (`window.setInterval(processDashboardQueue, 5000)`, gutenberg-finalizer-admin.php:682) — grepping
   the admin page, `runtime.php`, and `rest.php` for `approve|reject|confirm|review|diff|preview`
   returns nothing relevant. There is no button a human clicks to approve content.
4. It renders each block in a hidden editor iframe to get the real block JS to serialize it, then
   POSTs the result to `/gutenberg/items/{id}/complete` (`complete_item()`,
   gutenberg/bootstrap.php:1757-1823), which stages the finalized markup in postmeta and marks the
   item `prepared` — still not live.
5. Once every item in a batch is `prepared`, `finish_batch_if_complete` runs the actual commit
   (bootstrap.php:1469-1522): for each item, an **optimistic-concurrency check**
   (`hash_equals($base_hash, content_hash($target->post_content))`, bootstrap.php:1464,1484) refuses
   to overwrite a post that changed underneath the batch, then `wp_update_post` writes
   `post_content`. If a later item in the batch fails mid-commit, already-written items are rolled
   back to their base content (`restore_written_prepared_items`, bootstrap.php:1536-1559) — a
   best-effort compensating rollback, not a true cross-post DB transaction.

**Access control on the queue itself** reuses ordinary WP editorial capabilities, not a new consent
mechanism: `rest_can_access_dashboard` requires `edit_posts` (rest.php:96); `rest_can_access_item`
requires `novamira_current_user_can_manage()` OR `edit_post` on the specific target
(rest.php:136-154). So *any* logged-in Editor/Author with edit rights on the target post — not just
a Novamira admin — can run the finalizer page and complete items, provided the batch/item already
exist (which do require `novamira_permission_callback`/`manage_options` to create). This is a sane
separation in principle (editors finish what admins/agents queued) but means the "human in the loop"
for a given change is *whoever happens to have the queue page open with edit rights on that post*,
not necessarily the person who approved the underlying instruction to change it.

**Is this pattern worth stealing for Jini?** As a *review gate*, no — there isn't one to steal. As an
answer to "the model can't render this itself, a real client-side runtime has to," it's a genuinely
clever, well-engineered solution (lease-based concurrency, staged commit, compensating rollback) to a
problem Jini would only face if it ever needed a third party's client-side rendering logic to
materialize agent-authored structured content. Section 7 discusses this further.

## 5. `includes/skills/` — what it is, and how it differs from an ability

A **skill** is a markdown procedure document — YAML frontmatter (`name`, `description`) plus a
freeform body — in the same shape as Anthropic's own SKILL.md convention. Confirmed by reading
`includes/skills/built-in/gutenberg-edit-content.md` in full: it is a step-by-step playbook telling
an agent *which abilities to call in what order* for Gutenberg work, including exactly the
finalizer-runtime polling instructions from §4.

Skills are stored either as a custom post type (`includes/skills/cpt.php`, user-authored via the
admin UI) or contributed by other code through the `novamira_skill_lookup_sources` filter
(`skills/bootstrap.php:45`); built-in ones ship as `.md` files under `skills/built-in/`.

**The ability/skill distinction, precisely**: an *ability* is one typed, schema-validated,
permission-gated function (`wp_register_ability`). A *skill* is not a function at all — it is
documentation that gets loaded into the model's context on demand, describing how to sequence
existing abilities. Discovery is a two-step, progressive-disclosure pattern that does map onto
Jini's own staged-search idea: the catalog block injected into `discover-abilities`'s instructions
(`skills/catalog.php:26-64`) shows only `slug`/`description`/source-label for every skill; the full
body is loaded only via a second call, `novamira/skill-get` (`skills/abilities/skill-get.php:65-107`).

**The one abilities-category ("shared category") registration point is worth noting for correctness**:
`skills/bootstrap.php:48-52` has a comment explaining a real bug they hit and fixed — registering the
`skill` ability category on the wrong hook (`wp_abilities_api_init` instead of
`wp_abilities_api_categories_init`) silently dropped every ability that declared `category: 'skill'`.
Not security-relevant, but a good illustration that this registry has sharp edges even for its
authors.

**The sharp finding, held for §7**: `novamira/skill-write`, `skill-edit`, and `skill-delete`
(`skills/abilities/skill-{write,edit,delete}.php`, all gated by the same
`novamira_permission_callback` as every destructive filesystem ability) let an agent write directly
into the exact catalog structure that `discover-abilities`'s instructions block — read by every
future session — is built from.

## 6. Honest security read

**The plugin's own framing is accurate, and its trust model is coherent for its stated deployment
target** — a single-tenant, self-hosted WordPress site with an admin-gated, opt-in toggle. Every
dangerous action requires `manage_options` (or multisite super-admin) *and* an explicit
`novamira_ai_abilities_enabled` option the site owner turned on *and* the site's own current domain
matching the domain it was enabled on (an anti-replay measure against DB-clone attacks,
`helpers.php:380-394`). Given that starting point — "I, the site admin, am choosing to let my own AI
agent act with my own privileges on my own site" — most of what looks alarming in isolation
(`eval()`, arbitrary `wp` subcommands, reading any file under ABSPATH) is not a *bug*: it is the
literal, disclosed feature. An admin already has equivalent power via SSH, a file manager plugin, or
WP-CLI directly; novamira is a remote-control surface for capabilities the admin already holds, not a
new escalation path *for that admin*.

**Where the real risk sits, and it is exactly where the dispatch prompt suspected**: prompt injection
from data the agent reads while holding `execute-php`/`run-wp-cli`/`read-file`. Once an agent with
these abilities is asked to, say, "summarize this contact-form submission" or "clean up this
imported post," and that submission/post contains adversarial instructions, there is **no code-level
boundary between "content the agent is reading" and "instructions the agent should follow"** — that
distinction lives entirely in the model's own judgment, the same failure mode `ai-control-plane.md
§19.5` names explicitly ("Database rows, files, web results... may contain adversarial
instructions... The agent prompt must not treat arbitrary retrieved content as authority"). Novamira
has no mechanism resembling that guidance anywhere in the traced code — none of the file-read or
`$wpdb`-backed abilities label their output as untrusted data versus instructions.

**Concrete findings, precise and citable, in order of how much they narrow the "for an already-
trusted admin, so it's fine" defense:**

- **`execute-php` has genuinely zero enforced restriction on *what* the code can do** beyond a 30s
  wall-clock limit — no disabled-functions list, no static analysis, no separate process, no
  `open_basedir`. Every safety rule ("never call exit()", "no infinite loops") is prose in
  `meta.annotations.instructions` (execute-php.php:71-88), i.e. addressed to a cooperative model, not
  enforced against an adversarial one. `run-wp-cli` is a second, equally unrestricted path to the
  same power (any `wp` subcommand, no allowlist) — the two abilities are redundant in what they can
  reach, which means the attack surface for "arbitrary code execution given `manage_options`" is
  doubled without doubling the defenses.
- **`read-file`/`list-directory` can reach `wp-config.php`.** Confirmed no exclusion exists anywhere
  in the codebase (grepped `wp-config` across `includes/` and `novamira.php`). This hands an agent
  (or anything that tricks the agent) the DB password and all four WP auth/secure/logged-in/nonce
  salt pairs in one call — the salts that back every session cookie and nonce on the site, including
  novamira's own OAuth-adjacent HMAC keys derived from `wp_salt()` (upload tokens, admin-access
  tokens, discover-abilities' delegation). One `read-file` call, if its output is ever shown to or
  acted on by an untrusted party, compounds into "everything cryptographic on this site is now
  forgeable."
- **`delete-file`'s protected list is 4 entries** (ABSPATH root, `wp-admin`, `wp-includes`,
  `mu-plugins`), not a general "anything WordPress needs to run" concept. It does not protect
  `wp-config.php`, `.htaccess`, any active plugin or theme directory, or `wp-content/uploads`. A
  hardcoded denylist of this shape will always be a step behind — the correct instinct (which Jini
  already applies elsewhere, per `ai-control-plane.md:148`'s explicit-allowlist rule for
  `ui.click`/`ui.fill`) is to enumerate what *is* allowed, not what is forbidden.
- **The sandbox is explicitly not a security boundary, and this is documented, not accidental**
  (`helpers.php:148-156`: "not a security isolation boundary for all filesystem writes... Authenticated
  Novamira administrators may intentionally read, write, edit, upload, and delete non-PHP files
  elsewhere"). Given that explicit framing, the PHP-execution-sandbox restriction is really about
  *operational* safety (crash containment, a single place to disable/delete generated code) rather
  than security in the adversarial sense. Within that framing it is well built: real crash detection
  (`sandbox-loader.php:23-41`), real safe mode, real `.crashed` recovery.
- **Disabling AI abilities does not stop already-deployed AI-written code.** The sandbox loader
  (`sandbox-loader.php:55-64`) `require_once`s every sandbox `.php` file on **every request
  regardless of `novamira_is_enabled()`** — the toggle stops new MCP calls, not code the agent already
  wrote to disk in an earlier session. A site owner who "turns Novamira off" after a bad session has
  not actually turned off the AI's footprint.
- **OAuth's cryptographic isolation is contained by, not a boundary against, the ability layer.** The
  RSA signing key and encryption key live in `wp_options` (`keys.php:35-51`), which is directly
  readable by `execute-php`/`run-wp-cli`/`$wpdb`. This isn't a new privilege escalation (reading it
  already requires `manage_options`, same gate as everything else) but it means OAuth buys no
  confidentiality guarantee against anything that has already reached the ability layer — worth
  knowing if anyone is tempted to treat OAuth-vs-ability-execution as two separately-trusted tiers.
  They are the same tier.
- **`discover-abilities`'s weaker permission callback** (`is_user_logged_in()` + `current_user_can('read')`,
  effectively any role) is a real, if minor, gap between who can see the ability catalog (any
  logged-in user with an application password) and who can invoke anything in it (`manage_options`
  only). Low severity — descriptions aren't secrets — but it is inconsistent with every other
  ability's gate for no stated reason.
- **The skills catalog is agent-writable** — see §7, held there because it is as much a design
  critique as a security one.

**What is well built, plainly stated:** the admin-access-link and upload-link exchange flows
(§2, both) are the strongest engineering in the repo — real HMAC/`hash_equals` hygiene, header-not-
querystring token delivery, single-use consumption with delete-before-validate ordering, capped
session lifetimes, no-store/no-referrer response headers, and (for uploads) re-validating the
destination against the live filesystem at consumption time rather than trusting the mint-time
snapshot. The Gutenberg commit path's optimistic-concurrency + staged-write + compensating-rollback
design (§4) is also careful work, independent of whether the surrounding "queue" framing is the right
UX. None of that changes the fact that the two rawest-power abilities (`execute-php`, `run-wp-cli`)
have no enforcement beyond the role check — the plugin's engineering quality is uneven across
abilities, concentrated in the newer/more bespoke flows and thin on the abilities that most resemble
"give the model a shell."

## 7. What Jini should take, and what it should avoid

### Take

1. **The 3-meta-tool dispatch shape is validating, not novel, but it's a real independent data
   point.** Novamira arrived at "a small fixed set of MCP tools (discover/get-info/execute) that
   dispatch into a larger internal registry by name" without reference to Jini's design — this is
   good corroborating evidence for `PROP-tool-catalog-discovery`'s `search_tools`/`describe_tool`/
   `activate_tools`/`execute_tool` shape and for keeping `execute_tool`/`execute-ability` as the
   fallback path for MCP clients that can't refresh a dynamic tool list (already named as a needed
   fourth verb in the proposal, §6.1).
2. **Progressive disclosure for procedure knowledge (Skills)**: name+description in the catalog,
   full content behind one explicit `get` call. This is a clean, working instance of exactly the
   staged-disclosure discipline the proposal wants for tools, applied to procedures instead. Worth
   modeling Jini's eventual "workflow"/routine surface on this shape if one is built.
3. **The admin-access-link and upload-link token patterns are directly reusable primitives** if Jini
   ever needs a "hand a short-lived, narrowly-scoped credential to a caller that isn't already
   authenticated" flow (e.g. a browser-automation session bridge, which `ai-control-plane.md §15.2`
   already gestures at as "UI-session action"): header-only delivery, `hash_equals` comparison,
   delete-before-validate single-use, capped session lifetime, destination/target re-validated at
   consumption rather than trusted from mint time.
4. **The sandbox-loader's crash-detection/safe-mode pattern** is a good operational safety net *if*
   Jini ever lets an agent deploy persistent server-side code (which nothing in the current design
   proposes) — worth remembering as "if we ever do this, here's how to make it recoverable," not as
   something to build now.
5. **The OAuth audience-binding discipline (RFC 8707, checking `oauth_client_id` against a single
   canonical resource identifier derived in one function) is worth copying literally** if/when Jini
   adds OAuth for any MCP surface — it is a small, cheap, correctly-applied check that prevents token
   reuse across resources.

### Avoid

1. **Do not let `execute-php`/`run-wp-cli`'s pattern — "raw execution primitive, gated only by a role
   check, safety rules delivered as prose" — become a template for anything in Jini.** This is
   precisely the shape `ai-control-plane.md §24` already forbids ("Generic writable `sql.execute`...
   bypasses app-service invariants, portability, confirmation semantics, and least privilege" and
   "Relying on hidden tools for security... Tool omission improves relevance but is not
   authorization"). Jini's existing refusal of model-supplied selectors and `evalJavaScript`
   (§24, and the explicit allowlist-attribute design at `ai-control-plane.md:148`) is the right
   answer; novamira is the fully-realized version of the anti-pattern Jini already chose not to build.
2. **Do not let discovery return the whole catalog unfiltered and unranked.** `discover-abilities`
   has no query, no limit, no staging — it is the single clearest violation, in a real shipped
   product, of `PROP-tool-catalog-discovery §6.1`/`§6.2` and `ai-control-plane.md §10.1-10.2`'s
   filter-before-rank, summaries-before-schemas discipline. Keep the proposal's staged
   `search_tools`→`describe_tool` split; do not add a "just list everything" convenience tool even
   for bootstrapping, since that convenience tool is exactly what tends to become the one every
   client actually uses.
3. **Never let an agent write the catalog it or future sessions read from.** `novamira/skill-write`/
   `skill-edit`/`skill-delete` do exactly this — an agent, gated by the same permission check as
   `execute-php`, can add or rewrite the procedure documents that get injected into every future
   session's instructions. This is a direct, concrete instance of the anti-pattern
   `PROP-tool-catalog-discovery §7.2` already names and forbids ("The agent may never write the
   catalog... Registration is a host/plugin-install action on a different surface with a different
   principal"). If Jini ever builds something skill/routine-shaped, keep authoring on a different
   principal/surface than the agent that consumes it, and enforce that split with a test per the
   proposal's own instruction, not a doc comment.
4. **Do not treat "the sandbox/allowlist is documented as non-security" as sufficient.** Novamira is
   honest that its sandbox isn't an isolation boundary — but the effect for an outside reader is the
   same regardless of the documentation: a narrow, static, hardcoded allow/deny list (4 protected
   paths, 5 sandboxed extensions) that will always miss cases. Jini's existing preference for
   explicit author-controlled allowlists (`data-agent-target=`/`data-agent-field=`, never a
   model-supplied selector) is the structurally sounder shape — keep extending that instinct rather
   than hardcoded path denylists if any filesystem-adjacent capability is ever added.
5. **Do not let "disabled" mean "no new calls" while previously-created state keeps running.**
   Novamira's sandbox loader still executes agent-written PHP after the feature toggle is off. Any
   Jini kill-switch (a capability profile, a plugin disable, a run cancellation) should be checked
   for this exact gap: does turning it off actually stop *artifacts already created* by the
   capability, or only stop *new invocations* of it?
6. **Do not let a scope system exist in name only.** Novamira's OAuth scopes (`read`/`write`/`mcp`)
   are cosmetic — every token collapses to the same boolean `mcp` grant. If Jini's own risk-tiered
   authorization (`ai-control-plane.md §13.1` risk classes, §19.2 least privilege) ever grows an
   OAuth-facing scope story, make sure the scopes returned by discovery/consent are the same scopes
   actually enforced at execution — a scope that's requestable but not enforced is worse than no
   scope, because it looks like a control that isn't one.
