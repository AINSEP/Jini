## Redaction design note — tokenize paths and secrets separately

The invariant is that ordinary location references remain useful while credentials never gain an exemption merely by appearing next to a location. A slash is both a path separator and a legal credential character. Whitespace can separate prose tokens or occur inside a path. Therefore neither “split on slash” nor “exempt everything beginning with a filesystem root” can decide this safely. The two reported cases are opposite failures of that same ambiguity: a glued credential inherits a location exemption, or a readable path continuation is treated as an opaque key.

Keep credential recognition owned by the existing shared secret policy and chat's existing `redactUserText` boundary. Specific evidence wins first: known credential prefixes, authorization syntax and labelled credential fields are redacted even inside a quoted path or URL. Do not add independent secret scanners in storage, transport or UI. Those boundaries should continue calling the same owner, with idempotent removal markers and non-secret count metadata.

Recognize locations as spans separately from credential candidates. Spans need explicit root, quoting and delimiter rules. A comma, pipe or invisible separator ends an unquoted location; it must never shelter the following token. Quoted paths may carry spaces. For hand-typed paths, readable identifier continuations can explain whitespace without turning an arbitrary following token into trusted path content. Credential candidates retain slash characters until evaluated; splitting a base64 key at each slash destroys the evidence that it is one long opaque value. Within a candidate overlapping a path, opaque segment evidence must still be checked rather than applying a blanket exemption.

The current `cf5571045` implementation already makes this narrow distinction: specific rules first, bounded location spans, readable path continuations, then opaque-segment/entropy checks. Its corpus tests Unix, Windows and UNC paths; quoted and unquoted spaces; punctuation and invisible separators; slash-bearing random values; known-prefix keys inside locations; and ordinary URL IDs. That is the smallest existing owner satisfying the two requested cases, so this lane adds no competing tokenizer or regex patch. An eventual lexer should be justified by additional reproducible failures and should replace this owner's span recognition rather than layer another exception system over it. A shared corpus should exercise ingress, storage, model history and transcript output; both secret absence and byte-exact preservation of legitimate paths matter.

Prefer typed fields when intent is available. Picked folders already travel as separate folder references (`c868a4e38`); keep those references out of free-text credential inference. Secure credential-card fields should go directly to their credential owner and never become chat text. Hand-typed free text still needs best-effort inference because a random-looking folder name and an unknown secret can be identical bytes. Do not promise perfect classification or broaden URL behavior as an incidental fix. Line 329's explicitly accepted residual is unchanged. A stronger guarantee would need explicit credential/path intent or known-secret matching with an approved source and lifecycle, not another broad path exemption.
