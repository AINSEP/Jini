- 2026-10-11: **Slow typing in long chats was CSS style recalculation, not React — and only showed up with a huge transcript.** In Tovu's assistant dock, typing in the composer lagged in a very long chat (plannie, ~12.7k DOM nodes, 3.5 MB of tool output with tool calls shown); a new chat was instant. React was already fine (0 message rows re-rendered per keystroke, 2–4 ms of script). The cost was the browser: each keystroke changes the textarea's DOM, and a host CSS rule using `:has(...)` with a sibling combinator (`.jini-message-assistant:has(> .jini-message-usage + .jini-message-actions--assistant) > *`) made Chrome re-match styles for the WHOLE document — ~50 ms of "Recalculate Style" per key. Fix in Jini chat (`packages/chat/src/react/features/chat-pane/styles.ts`): transcript rows get `content-visibility: auto; contain-intrinsic-size: auto 160px; overflow-clip-margin: 8px` (inside `@supports (overflow-clip-margin)`, else focus outlines clip), so off-screen rows skip style/layout/paint while staying in the DOM (find-in-page, screen readers, agent DOM readers). Result: style 50.7→8.4 ms, keystroke-to-paint 72→16 ms. **Next time:** (1) test UI with worst-case data (long chats, 1,000-row tables, big media libraries), not empty states; (2) jsdom/React render counts CANNOT see CSS cost — measure in a real browser (Long Animation Frames API `styleAndLayoutStart`, or a Chrome DevTools trace, e.g. via the chrome-devtools MCP server); (3) treat `:has()` — especially with `+`/`~` or broad right-hand selectors like `> *` or `span:first-of-type` — as a performance hazard on pages that change on every keystroke; prefer a modifier class set by the component; (4) long lists get `content-visibility: auto` by default.
