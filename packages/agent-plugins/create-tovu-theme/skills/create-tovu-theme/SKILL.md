## Scope

This skill only applies inside a **Tovu** repo checkout — theme structure is a Tovu-specific
concept, not a Jini one. All paths below (`development/docs/themes/...`, `src/themes/...`) are
relative to the Tovu repo root. If there's no Tovu checkout in scope, this skill doesn't apply.

## Before anything else — confirm this is really what's wanted

This skill scaffolds themes to the **v2 TARGET design**
(`development/docs/themes/theme-authoring-guide-v2.md`), which the guide's own banner states
**does not exist in the running system** — no loader, renderer, or validator reads `render/`,
`partials`, `apiVersion`, `ai/`, or `tests/` today. A theme built by this skill will NOT load or
render in Tovu until someone builds the migration + validator described in guide v2 §19.

If the user just wants a theme that works right now, stop and point them at v1
(`development/docs/themes/theme-authoring-guide.md`) instead — do not silently scaffold v2 for
someone who actually wanted a working theme.

If there's no clear prior confirmation that v2 is the deliberate choice, ask once: "This scaffolds
the *planned future* theme structure (v2), which won't load in Tovu until that migration ships.
Want v2 anyway, or the real v1 structure that works today?" Skip the question only if the request
already specifies v2 / the target design / "the structure we outlined."

## Step 1 — Gather the essentials

Ask (batch into one question if more than one is missing):

1. **Theme id** — lowercase, hyphenated, must equal the folder name (enforced today, stays true in
   v2 — guide v2 §18).
2. **Tier** — `static`, `templated`, or `declarative`. (`code` is unbuilt in both v1 and v2 — refuse
   it, guide v2 §7/§17.5.)
3. **Authored or compiled?** Only `static` tier supports `compiled` (`build.source: "compiled"`
   requires `tier: "static"`, guide v2 §6 — this rule is REAL, already enforced by
   `theme.ts:643-645`, true in both v1 and v2 shapes).
   - **Authored**: hand-written HTML/Liquid/JSON, no framework build.
   - **Compiled**: theme is generated by a framework build (React/Vue/Angular today; the v2
     vocabulary widens this — guide v2 §6). Needs a `sourceDir` with the framework-native source.
4. **Name, description, one-line purpose.**

## Step 2 — Scaffold the folder tree

Root: `src/themes/static/<id>/`, `src/themes/templated/<id>/`, or `src/themes/declarative/<id>/`
matching tier (mirrors today's real layout convention — v1 folder structure — even though file
*contents* inside follow v2).

### Authored (any tier) — guide v2 §3, §17.1/§17.3/§17.4

```
<id>/
  theme.json
  tokens.json
  LICENSE                    # stub is fine — see Step 3 note
  css/theme.css
  render/
    pages/index.html         # (.liquid for templated, .json for declarative)
    partials/nav.html
    partials/footer.html
```

Add `render/layouts/`, `scripts/` (skip for `declarative` — FORBIDDEN, guide v2 §16), `assets/`,
`locales/` only if the theme actually needs them — don't scaffold empty dirs nobody asked for.

Do NOT create `ai/`, `tests/`, or a root `AGENTS.md` — guide v2 §12/§13 states these have **zero**
implementation anywhere, not even a stub format worth pre-filling.

### Compiled (`static` tier only) — guide v2 §4, §6, §17.2

```
<id>/
  theme.json                 # build.source: "compiled" — see Step 3
  <sourceDir>/                # e.g. "authoring/" — framework-native, untouched by these rules
  css/theme.css               # GENERATED — from the framework build, adapted into this shape
  render/pages/index.html     # GENERATED — from the framework build, adapted into this shape
```

Two things the guide is explicit about — do not gloss over either:

- **Nothing in the Tovu repo automatically converts a framework build's output into
  `render/`/`css/` shape.** `code-tier-asset-normalizer.ts` exists but has zero production callers
  (guide v2 §6). The generated tree has to be hand-adapted (or the normalizer wired up first, if
  that's in scope).
- **`build.artifactHashes` is REQUIRED and actually enforced** (`theme.ts:650-651`,
  `checkBuiltThemeConformance`, guide v2 §6) — a theme missing or mismatching a hash for any
  generated file loads `status: "invalid"`. After the generated tree is final, compute hashes:
  ```bash
  cd src/themes/static/<id>
  find css render -type f -exec sh -c 'echo "\"$1\": \"sha256:$(shasum -a 256 "$1" | cut -d" " -f1)\""' _ {} \;
  ```
  Paste the output into `build.artifactHashes` in `theme.json`.

## Step 3 — Write `theme.json` (schema v2, guide v2 §5)

Fill only the fields the tier needs:

- `id`, `name`, `version`, `tier`, `description` — REAL today, keep as before.
- `tokens: { defaultMode, modes: { <mode>: "<file>" } }` — TARGET restructure of the REAL flat
  `defaultMode`/`modes` fields (guide v2 §5, §15). `defaultMode` MUST be listed in `modes`
  (enforced, `theme.ts:635-639`).
- `partials` (not `slots`) — TARGET rename, guide v2 §10. Same per-entry shape as today's real
  `slots`: `{ source, honorsCurrentPage?, variants? }`. Do NOT use the `activeAttr` legacy spelling.
- `renderer.adapter` / `renderer.pages` — TARGET, unread by anything (guide v2 §15). Fill in for
  completeness, don't treat as load-bearing.
- `license: { spdx, file }` — TARGET; still create the `LICENSE` file itself, since no theme ships
  one today (guide v2 §14) and this is a good time to stop that pattern.
- `regions: string[]` — REAL and wired (guide v2 §9) — a flat array of region-key strings, e.g.
  `["header", "footer"]`. Only add if the theme actually places widgets in a region; don't cargo-cult
  it onto every theme.
- `build` (compiled only) — REAL, see Step 2. `source: "compiled"`, `framework`, `sourceDir`,
  `artifactHashes`. Note `framework` is a **closed union today** — only `"react"|"vue"|"angular"`
  parse; anything else silently drops (guide v2 §6). If the real source framework isn't one of
  those three, say so in `NOTICE.md` and still pick the closest of the three for `framework` (or
  omit it) rather than inventing a fourth value.
- Skip entirely: `ai`, `apiVersion`, `$schema`, `scripts.entries`, `assets.previewGallery`,
  `authors`/`attributions` — **all confirmed zero-consumer** (guide v2 §15 table). Adding them
  costs nothing but also does nothing; don't spend the user's time filling them in as if required.

## Step 4 — Sanity-check against guide v2 §16 by hand

No validator exists to run. Check manually:

- [ ] Folder name === `theme.json` `id`
- [ ] `declarative` tier has no `scripts/`
- [ ] compiled theme: `tier === "static"`, `build.sourceDir` non-empty, `build.artifactHashes`
      non-empty and covers every real file with a correct hash
- [ ] `build.sourceDir` does not collide with a reserved generated dir name like `preview`
      (open gap, guide v2 §6/§19 item 1 — check by hand since nothing else will)
- [ ] no `data-agent-element` attribute anywhere in theme markup (admin-only, not theme markup)
- [ ] every `templates` entry resolves to a real `render/pages/<id>.html`-equivalent with at least
      one content marker

## Step 5 — Tell the user what they actually have

Always close with a plain-language recap, not just "done":

- This theme will **not appear or render** in Tovu until the v2 migration/validator ships (guide v2
  §19 — still an open punch list, nobody has started it as of this writing).
- What's on disk is a correctly-shaped v2 scaffold, ready to become real the moment that migration
  exists — not a working theme today.
- If they actually need something rendering *now*, the fastest path is a v1-shaped `static`-tier
  authored theme (flat `pages/`/`css/`/`js/` at the theme root, no `render/` nesting) — offer to
  build that instead/in addition if that's really the goal.
